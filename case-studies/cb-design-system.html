Overview

This case study outlines the end-to-end process of building a scalable design system using Figma. It covers the initial setup, component creation, token and variable management, developer collaboration, accessibility integration, governance practices, and ongoing education through design system office hours.

01

Foundation Setup & Planning

  • Audited existing UI across products to identify inconsistencies.
  • Defined goals: consistency, scalability, accessibility, and developer alignment.
  • Chose Figma as the central tool for all design system work.
  • Created the initial design system file structure:
    • Foundations (colors, typography, spacing and layout grid)
    • Components (buttons, inputs, modals, etc.)
    • Templates and examples
02

Component Architecture

  • Built foundation components first (icons, text styles, spacing blocks).
  • Progressed to composite components (buttons, form fields, cards).
  • Created variants for states (default, hover, disabled, loading).
  • Set up auto layout and constraints for responsive behavior.
  • Used Figma's component properties and boolean toggles to manage complexity.
03

Token Strategy & Theming with Variables

  • Created foundational variables:
    • Color variables: primary, secondary, background, surface, etc.
    • Spacing: spacing-4, spacing-8, spacing-12...
    • Typography: font-size, font-weight, line-height
  • Grouped variables into collections: Light theme, Dark theme, Brand
  • Used semantic naming: color-bg-primary, spacing-md, font-body-lg
  • Synced tokens with development
  • Aligned naming conventions with code for better handoff
  • Ensured the system could be reused across different products with slight theming variations (e.g., light/dark mode and brand-specific tweaks)

Tokens POC

  • Built a two-layer structure:
    • Layer 1: Raw variables for physical values
    • Layer 2: Semantic tokens that reference the raw ones
  • Enabled smooth theming and context-aware design, while reducing duplication
  • Developers and designers could now align easily, knowing which tokens to apply for context vs. hard-coded value

04

Semantic vs. Raw Variables: Structuring for Flexibility and Scale

  • Raw variables represent base values like #007AFF or 16px, typically named for their design trait (e.g., blue-500, font-size-16). These are foundational and remain consistent across themes.
  • Semantic variables are mapped to raw variables and named by purpose (e.g., color-bg-primary, text-body, spacing-content). These make the system adaptable to themes like dark mode or brand customization.
05

Developer Collaboration & Accessibility Integration

  • Held weekly design-dev syncs to review component specs.
  • Shared interactive prototypes and inspectable files via Figma.
  • Exported and documented tokens for dev integration.
  • Aligned on version control, naming structure, and update cadence.
  • Used storybook to test parity between coded and Figma components.
  • Defined contrast ratios using Figma plugins (Able, Stark).
  • Used semantic HTML as reference for structure.
  • Incorporated keyboard navigation and screen reader notes into documentation.
  • Reviewed components with accessibility engineers.
06

Component Documentation

  • Created detailed documentation for each component in the design system.
  • Each documentation page includes:
    • Component description and use cases
    • Properties and states supported (e.g., size, icons, alignment)
    • Behavioral specs for interactions like hover, focus, disabled, and loading
    • Accessibility annotations including role, aria attributes, keyboard focus
    • Do's and don'ts for designers and developers
  • Updated documentation regularly alongside new component releases and changes to variables or design tokens
  • Versioning was applied to each update, and all updates were synced with the development team to ensure design and code stayed aligned
07

Governance Model & Design Contribution Process

  • Created a governance model:
    • Design system team owns updates
    • Designers submit requests via a wishlist page in each flow Figma project file
    • Bi-weekly reviews for new components or changes
08

Education & Engagement: Design System Office Hours

  • Hosted bi-weekly office hours with designers and developers
  • Agenda included:
    • New component walk-throughs
    • Token and variable changes
    • Open Q&A
09

Challenges

Challenges & Lessons Learned

Adoption gaps

Some teams didn’t use the system or made their own. We ran trainings and helped them migrate.

Theming complexity

Supporting light and dark themes was tricky. We solved it using semantic tokens.

Manual overrides in Figma

People broke components. We taught best practices and used plugins to catch issues.

Accessibility retrofits

Early components missed a11y. We added checks and involved accessibility experts.

10

Outcomes & Success Metrics

Building a design system in Figma required deep collaboration, clear naming, governance, and a strong focus on accessibility. Office hours and developer alignment played a critical role in driving adoption and ensuring long-term success across multiple products and themes.
